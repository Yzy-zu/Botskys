# R2 · recorrido durable mínimo

Entrada sintética de operador local → frescura/corte → parser determinista →
permiso backend → recibo durable → handler tipado → efecto/resultado atómicos →
outbox por partes → aceptación local registrada.

Disponibles: /ayuda, /estado ID, /cancelar ID, /nota guardar TEXTO y /notas
[--pagina N] [FILTRO]. Otras rutas devuelven capability_unavailable con su bloque;
administración se deniega antes del dispatcher a quien no sea dueño. Las llamadas
no están configuradas. Un adjunto o texto no comando no crea trabajo.

Para comprobar el parser sin DB:

```bash
PYTHONPATH=src .venv/bin/python -m botsky parse '/nota guardar -- Comprar --pan'
```

Laboratorio con configuración propia (no instala servicios):

```bash
PYTHONPATH=src .venv/bin/python -m botsky init
PYTHONPATH=src .venv/bin/python -m botsky local '/nota guardar Comprar cable' --message-id ejemplo-nota
PYTHONPATH=src .venv/bin/python -m botsky local '/notas cable' --message-id ejemplo-busqueda
```

Cambiar el contenido conservando message-id produce message_conflict. Repetir
el mismo mensaje fuente devuelve su recibo; el adaptador deberá conservar también
el timestamp de origen. CLI local crea timestamp actual en cada invocación y
está pensado para mensajes sintéticos nuevos; no es simulación de reentrega WhatsApp.

Separa permisos de sintaxis; actor/chat son metadatos de operador, no autoridad
remota. Evolution deshabilitado expresamente. No se abre puerto ni conexión de red.
Config v1 exige la zona America/Mexico_City, listas explícitas y corte con zona;
la DB debe estar dentro del proyecto de esa configuración.

Datos de laboratorio en private/botsky.sqlite3: esquema propio v2, solo fixtures
que se creen expresamente. No usar esa DB como datos iniciales de transición:
R11 deberá crear almacenamiento vacío y una época/corte nuevos.

Entrega local es aceptación del sink/STDOUT, no lectura humana. Una excepción,
ACK inválido o interrupción al enviar deja uncertain y bloquea repetir esa parte.
Solo un rechazo explícito known-failed permite retry_failed de entrega, nunca de
la herramienta. Partes aceptadas no se vuelven a mandar. El API de recuperación
de sending exige obtener antes propiedad exclusiva del proceso (R3).

Comprobaciones de R2: duplicados/reinicio, actor/chat/época, corte/histórico/reloj,
permiso revocado entre admisión y efecto, cancelación ajena, atomicidad con crash,
filtros/%/_/páginas/vistas entregadas, CAS de entrega y envío fuera de transacción.
R0/R1 conservan sus evidencias originales; R2 añade su log y acta separados.
