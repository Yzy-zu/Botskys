# R6 · Drive y recados

Construcción local cerrada. Drive/messenger se inyectan explícitamente en
Application; por defecto siguen sin configurar. No hay acceso a secretos o
transportes de Zhana ni conexión real de CLI a servicios externos.

Drive reserva trabajo propio y lease del archivo, con hash verificado antes del
motor. Carpeta y scope actor/chat/cuenta/época ligados al trabajo y a la vista.
Buscar devuelve hasta cinco candidatos; elegir requiere vista propia entregada
vigente5min y vuelve a comprobar metadatos, carpeta, scope y tamaño. Se entrega un
artefacto local inspeccionado por firma; no se usa nombre remoto como ruta local.
Cuota de cuenta solo dueño. Guardar genera ID remoto y lo persiste antes de subir;
recibo drive_uploads conserva ID, carpeta, scope, SHA256 y estado. Resultado
incierto se concilia con GET del mismo ID en el cliente, sin segundo POST/PUT.
Corte de proceso después del dispatch queda incierto sin reiniciar la subida;
no se afirma que un remoto desconocido se haya creado o borrado.

OAuthToken es nuevo: solo private/drive del root propio pasado explícitamente,
archivos client.json (client_id/client_secret) y token.json (refresh_token), modo
0600 y sin symlinks. Refresh único bajo lock, sin redirecciones/reintentos y con
respuesta acotada; rota refresh token con replace/fsync. Acceso breve en memoria.
No se inició autorización Google ni se leyó una credencial real. Provisión real
requiere el encargo posterior de integración.

Recados: /contactos lista nombres configurados; /recado preparar exige dueño en
privado, destinatarios exactos, texto literal actual o cita propia y adjunto propio
opcional10MiB. Lista parcial/ambigua se rechaza. Una sola vista activa por ámbito,
con nombres, contenido y hash/formato/tamaño del adjunto; no hay cargo ni envío al
preparar. /recado enviar ID exige preview completo aceptado, entrada posterior a
esa entrega, TTL5min, mismo ámbito/directorio y proveedor configurado. Reserva
atómica del trabajo y partes por destinatario; solo se reclama pending una vez.

Se revalidan dueño, modo, directorio y vigencia antes de cada parte. Un ACK válido
se registra como aceptación, no recepción humana. Rechazo conocido es failed;
fallo tras dispatch es uncertain; partes restantes se cancelan. Corte/reinicio no
repite aceptadas/inciertas. Cancelación retira partes pendientes, conserva la parte
incierta y cualquier aceptación tardía verificable. /recado estado ID muestra
recibos, /recado cancelar ID no promete retirar una parte ya enviada. Messenger
usa HTTPX contra endpoint configurado, sin retries/redirects, solo sendText/media;
ninguna salida IA ni texto de cita pasa por el router.

Pruebas: SQLite real, HTTPX/MockTransport y un servidor HTTP loopback efímero para
el cliente de recados, sin Evolution remoto. Fixtures sintéticas, bytes de adjunto
reales, carreras/reinicio/cancelación/ID reservado/selección/roles y OAuth privado.
Evidencia R6-closure-tests.txt, R6.json. Google/Evolution/WhatsApp/Android reales y
lectura humana NOT_TESTED. Sin instalación, navegador, servicio ni GitHub.
